Use ASP.NET Core Identity for local accounts/password verification, the existing long actor IDs, controlled first-admin creation, sign-in/out, explicit session eligibility, and the minimum membership/fixed-role assignments needed by OrganizationUseCases. Framework types belong in Infrastructure/Web, never Domain. Deliver real ITrustedActorAccessor and IOrganizationPermissionEvaluator implementations; HTTP cookie/antiforgery operations; server circuit revalidation; profile language persistence and identity-boundary draft clearing; minimum security-event persistence; bilingual login/logout/access-denied UI. Framework support tables do not authorize those features.

## Bootstrap without circular authority

Proposed host-only `initialize-deployment` command is absent from HTTP routing and startup seeding. It requires an explicitly authorized deployment operator in the normal host identity and a separately protected provisioning DB connection. It refuses normal application credentials and refuses a populated deployment needing reconciliation. No shared/default password, URL setup secret, sandbox SID provisioning or public setup endpoint.

1. Acquire the singleton BootstrapState row lock in a serializable transaction. Require Pending state and no existing account/Organization/Site. Initialize only an inspected fresh installation; an existing one needs a separately reviewed reconciliation plan.
2. UserManager creates the actual first account with a password entered through a protected interactive prompt by its owner. Obtain its real positive long ID. No zero/system/fabricated user is inserted for attribution.
3. The narrow bootstrap coordinator creates one Organization and one Site through existing Domain factories. It supplies ControlledBootstrap provenance, the allocated account ID, operation GUID and server correlation. The security event separately identifies the host operator: attribution to the new account does not claim that account was already signed in.
4. Write the existing OrganizationChange records, first Organization/Site memberships and company-only OrganizationAdministrator assignment, bootstrap security events and Completed state in that same SQL transaction. A1 has no platform-grant flag or automatic deployment authority.
5. Commit before reporting success. Failure rolls everything back. On an uncertain commit, query the stored operation/state before any rerun; never replay initialization blindly. Completed permanently closes first initialization. Repeating the completed operation reports status without changing credentials or grants.

Integration seam: the current OrganizationOperationsStore/public use cases own their transactions and must not be chained inside an outer bootstrap transaction. AUTH-01 must implement a small host-only coordinator sharing one SQL connection/transaction between an operation-scoped Identity context and the existing internal attributed organization-save path. It reuses Domain rules and audit persistence, not permissive runtime adapters or a general transaction framework. This narrowly authorized bootstrap path validates host authority and first-initialization conditions itself; ordinary requests always use the existing secured use cases and real adapters. Prove atomicity and concurrent initialization before enabling bootstrap.

A1 implementation: `tools/ForgeFlow.Bootstrap` is a separate executable, not referenced or registered by Web. It requires an interactive non-redirected private terminal, explicit INITIALIZE attestation and `FORGEFLOW_BOOTSTRAP_SQLSERVER` supplied privately. It records the actual host identity but checks authority through dedicated provisioning capability (dbo/db_owner, excluding the auth/business runtime roles), not a fixed OS account allowlist. Never put a password in arguments, environment variables, source, logs or receipts; the initial password/confirmation use hidden Console.ReadKey input, with no character echo or silent truncation. The command accepts exactly one verb and no password/deployment-grant arguments. Target server/database are shown before confirmation, never credentials. Keep the terminal free of transcripts and remove the connection variable after the session.

Prerequisite: review/apply the existing business baseline and the additive auth migration to an explicitly approved target through the separate deployment process. The initializer never migrates/seeds on startup, rejects system database targets and returns SchemaNotReady for pending migrations. Its empty state means only schema/history plus Pending singleton exist. Pending with any pre-existing account/business/access/security/support data, or a missing/inconsistent completion record, returns BootstrapPartial without adoption/repair. Completed returns BootstrapClosed; a consistent same-operation replay with matching immutable user/code identifiers returns AlreadyInitialized without credential/grant changes. Codes/names use the existing Domain factories; UserManager creates/hashes the real first account. The fixed role is company-only, both memberships are scoped to the actual generated IDs, and no session is issued.

After the operator has privately configured the dedicated provisioning connection and reviewed the target, the manual command is:

```powershell
dotnet run --project .\tools\ForgeFlow.Bootstrap\ForgeFlow.Bootstrap.csproj -c Release --no-build --no-restore -- initialize-deployment
```

This intentionally initializes data and must not be run against an unreviewed or pre-populated installation. Keep the displayed non-secret operation ID to resolve an uncertain commit through a consistent replay. The command performs no automatic retry. SQL/Identity exception text and credential material are not printed; identity rejections expose only stable error codes. The user reports successful native interactive hidden-input initialization; the agent did not execute it, and database cleanup is unreported. See test-plan.md for disposable SQL tests before use.

## Runtime flow and boundaries

Sign-in is a static HTTP form POST, using Identity password/lockout services, antiforgery, generic credential errors, and local allowlisted return URLs. Validate current account eligibility, persist a session plus SessionIssued security event, then issue the Identity application cookie and fully reload. A cookie-write failure cannot be atomically rolled back with SQL; an orphan issued session is unusable without its protected ticket and expires normally. No success claim before the session transaction commits.

Sign-out is HTTP POST with antiforgery: revoke the current session server-side, record the event and expire its cookie, then clear identity-scoped drafts and full reload. Other browser sessions are independent; all tabs sharing that cookie/session lose access. Password reset/disable/global security-stamp change invalidates all that user's sessions. If revocation persistence fails, expire this browser's cookie anyway, show localized revocation-failure feedback and never claim other sessions were revoked. A DB outage denies subsequent protected operations rather than trusting cached claims.

Proposed stable boundary codes: Auth.LoginRejected (same public failure for unknown/invalid/ineligible credentials), Auth.SessionInvalid, Auth.AccessDenied, Auth.ServiceUnavailable, Auth.LogoutRevocationIncomplete, Auth.BootstrapClosed, Auth.BootstrapIneligible, Auth.ResetRejected and Culture.ProfileSyncFailed. Parameters are safe field names/limits or supported culture codes, never credential/stamp/token values or forbidden entity data. The presentation adapter inventories and localizes framework Identity error codes with typed parameters through .resx; it does not surface raw framework descriptions or exceptions. Preference-only updates must not rotate SecurityStamp or invalidate sessions.

No cookie mutation from an already-running circuit callback. HTTP middleware and each protected service operation validate current database user/session eligibility; the permission adapter additionally validates exact owner, current active memberships and fixed scoped role. Claims carry identity/session references, never authoritative roles, memberships or permissions. Circuit actor resolution uses server-established authentication state, not a captured circuit HttpContext or a posted actor ID. ProvenanceReference is the server session GUID; correlation is generated server-side per operation.

Revalidation proposals: database checks on every protected use case and each cookie-authenticated HTTP request; circuit proactive checks every 30 seconds while running, plus before protected rendering after resume/reconnect. The timer is UI cleanup, not a permission cache or a substitute for operation checks. On invalidation mask protected content, stop data access, clear app drafts and force a fresh HTTP identity boundary. Background browser suspension can delay visible cleanup; server operations remain denied. Cross-tab signals accelerate cleanup but cannot authorize anything.

## Minimum recovery and maintenance

Recommended initial recovery is supervised host-operator password reset, with the account owner verified out of band and present to enter a new password in a protected prompt. Use Identity's reset-token/password pipeline entirely in the process; never display/store/log the reset token or password. Record the host actor and subject user separately, update security stamp and revoke sessions atomically. Lost first-admin password does not require an already-authenticated application admin; approved host authority is the recovery boundary. No public forgot-password/token-disclosure endpoint or unconfigured email sender. Login shows localized instructions to contact the deployment operator. The operational acceptability of this path is Q-A1.

Account eligibility, session revocation, membership and fixed-role enable/disable backend operations are needed for acceptance and later administration, but no user/role administration screens or generic CRUD are included. Initial grants come only from bootstrap inputs; extra accounts/grants in integration tests are created through real Identity/services in test fixtures. Later production provisioning UI/tooling is a separately authorized slice; this design does not authorize ad-hoc SQL changes as an administration workflow. Recovery must not reactivate a disabled account or restore revoked memberships.

## Language, drafts and UI

Preserve FF-A016 precedence: supported browser culture cookie, then authenticated profile preference, then Accept-Language, then fa-IR. An explicit browser choice survives sign-in and logout; login does not silently overwrite the account preference. Only an explicit authenticated switch writes the current user's profile through a server-validated adapter. Unsupported values are rejected. A known profile-save failure may still apply the browser cookie, but response/UI must say CookieApplied/ProfileSaved separately with a localized warning; never claim synchronization. Capture drafts before switching and restore raw invalid values/validation codes using the existing coordinator. Profile-fallback language must be resolved before a new request/circuit renders; localization order must support validated cookie identity without mutating process-wide defaults.

Draft identity scope includes server user ID, session generation, organization/site, route/form and schema. Clear application-owned drafts on login, logout, account/session switch and lost scope; never promote anonymous/previous-session drafts into an authenticated identity. Keep per-tab isolation. A same-origin nonce-only identity-change signal prompts other tabs to mask/reload/clear their own sessionStorage; it contains no credential or grant. On resume, validate identity before restoring any draft. Best-effort JavaScript cleanup is not access control: mismatched server scope is always rejected. Passwords/tokens/cookies are never in drafts, browser storage or diagnostic logs.

Login page: `/account/login`; HTTP credential submission: `POST /account/sign-in`; logout: `POST /account/logout`; proposed denied page: `/account/access-denied`. Page and command paths must remain distinct because Razor component routes accept POST as well as GET. No logout page currently shares its command route. Only login is anonymous; denied UI reveals no forbidden resource names. Logout remains available to a currently recognized session even when company membership is revoked. Authenticated sample language switching exercises real profile persistence and failure; no new generic profile form. Require fa-IR/en-US, RTL/LTR, keyboard navigation, focus/error announcement, localized Identity errors/parameters and desktop/320px no-overflow acceptance. After login/logout use real HTTP redirects/full reload; local return destinations are checked and reauthorized. An inactive company with an explicit lifecycle grant remains discoverable for reactivation; no global organization directory is introduced.
